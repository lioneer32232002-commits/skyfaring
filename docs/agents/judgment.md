# 判斷守則（何時完成・何時問人・何時換路）

> 讀者：未來在本專案工作的模型。每條判準盡量附正例與反例，例子出自本專案 git 歷史或
> CLAUDE.md／AGENTS.md 既有規則；挖不到真實案例的小節誠實標「尚無本專案案例」，
> 不編造。抽象原則只有一條：**先有證據，才有宣稱**。其餘全部是可執行的檢查。

## 1. 何時算「真的完成」——按改動類型查表

宣稱完成前，把對應列的每一項做完並**留下輸出證據**（指令輸出、截圖、零 diff 確認）。

### 文章（content/posts/）改動
- [ ] `node scripts/check-post.mjs content/posts/<slug>.md` 零 ERROR；WARN 逐項判斷
      是不是「來源原文真的這樣用」，不確定的問使用者
- [ ] frontmatter 必填欄位齊全（title/author/date/slug/tags/excerpt/heroImage/
      heroAlt/heroCredit/heroCreditUrl/highlight），`author` 固定值，`slug` 與檔名一致
- [ ] 有數據/引述的說法都對過來源（自己查或派 `data-checker`）
- [ ] hero 圖是橫式、比例正確，不是誤植直式圖
- [ ] 中英文/數字之間有半形空格（盤古之白）

**反例**：commit `efed017`／`b446022`——11 篇文章的 hero 圖用了直式圖，OG 分享圖比例
錯了才回頭修正 1200x630 橫式。上線前沒有核對圖片方向/比例。
**反例**：commit `f3ae356`——「盧冠軒三分球數據 6投10中 → 10投6中」，投籃數順序寫反，
資料查核沒抓到就先上線，事後才修。**數字型敘述（X 投 Y 中、比例、百分比）順序容易寫反，
要逐字核對來源，不能憑印象順。**
**反例**：commit `4d38b12` / `88961bb`——`author` 欄位錯過不只一次，才把它做成
`check-post.mjs` 裡的固定值 ERROR 檢查。**同一種錯重複出現，代表該補進機械化檢查，
而不是每次靠人記得。**

### 程式改動（元件、儀表板、scripts）
- [ ] `npm run lint` 通過
- [ ] `npm run build`（static export）通過，沒有型別或建置錯誤
- [ ] 涉及環境變數/外部服務（Supabase 等）的改動，確認缺失時是**優雅降級**而不是整頁掛掉
- [ ] preview 實際載入被改的頁面，操作到被改的流程

**反例**：commit `e39bde9`「硬化 Supabase 用法：環境變數缺失時優雅降級，不再整頁壞掉」——
原本 env var 沒設就會讓整頁壞掉，是後來才補上的邊界條件處理。**改動任何讀環境變數/
外部服務的程式碼，都要想清楚「這個值不存在時會發生什麼」。**

### 自動化排程（automation/、scripts/generate_game_article.py 一類）
- [ ] 觸發時間類設定改完，核對 `automation/runlog-*.jsonl` 確認實際觸發時間，
      不是只改設定值就假設生效

**反例**：commit `a1c8d07`／`8864f8b`——自動發文的備援觸發時間先後改了兩次
（晚上 9 點 → 9:30）才穩定。**時區/排程時間類設定屬於「看起來改一行就好，
實際要跑過一輪才知道對不對」的類型，改完要等下一次排程週期驗證，不能改完就當作完成。**

## 2. 何時停下來問使用者

**問**（動手前）：
- 刪除或重寫寫作規範既有規則——AGENTS.md 明文規定「要刪除或重寫既有規則，
  先徵得使用者同意」，只能新增條目或修正明確錯誤
- 內容收錄與史觀定性判斷（例如歷史推演類文章要怎麼定性、哪些說法要不要收）
- 產品設計取捨：新功能形態、視覺風格、文案語氣
- 規則與現實衝突：CLAUDE.md 說 A、現況是 B，選哪個

**不問**（直接做）：
- 修 `check-post.mjs` 抓到的 ERROR、明確錯字
- 規則已明文寫在 CLAUDE.md／`.claude/agents/`／`.claude/commands/` 的事
- 可逆、範圍小、且是使用者原始要求的直接延伸

**正例**：AGENTS.md「規則維護協議」——寫作規範新增禁用句式要同步改
`scripts/check-post.mjs` 正則，兩者放同一個 commit；規則的刪除/重寫則保留給使用者決定，
不由模型自行拍板。
**尚無本專案案例**：內容收錄判斷的具體正反例，踩坑後照 maintenance.md 第 3 節補回本節。

## 3. 何時升級模型或求援

- AI 寫作腔（尤其「重新框定」骨架殘留）判斷不準 → 讀 `docs/writing-style-examples.md`
  的四步判別法與對照例，這份文件就是為了讓「較小模型」也能判別而寫的
  （commit `737b12a`「新增骨架級判別對照例檔，供之後較小模型判別重新框定殘留」）
- 事實查核來源互相矛盾，或本地論文庫查不到 → 升級到 opus 級判讀原文，
  或標註「無法核對」回報使用者，不要用印象補完
- 同一子任務被退回兩次 → 帶失敗軌跡升級（詳見 dispatch.md 第 6 節）

**尚無本專案案例**：「品味判斷需要升級」的具體正反例，踩坑後補回本節。

## 4. 方向錯了的訊號（該換路，不是再試一次）

出現任何一條，停止當前路徑，回到源頭（CLAUDE.md 規範、原始來源、最小重現）：

- 同一修法失敗 2 次，第 3 次只是「再試一次看看」
- 想放寬 `scripts/check-post.mjs` 的檢查規則，讓自己的文章通過驗證
  （等於拆保險絲——這份腳本就是照過去踩過的坑一條條加出來的）
- 想用規則猜圖片授權/來源而不查證（CLAUDE.md 配圖流程要求確認授權與攝影師姓名，
  不能假設「這張圖看起來免費就能用」）
- 想手改 `reviews/*.html` 一類疑似生成物來修症狀，而不是改對應的 `build_*.py`
- 修 A 壞 B、修 B 壞 A 的循環——代表理解錯了共同的上游

**尚無本專案案例**：完整的「同一路徑失敗兩次」正反例，踩坑後補回本節。

## 5. 品質底線怎麼驗（evidence before assertion）

- 每一句「已完成／已修好／已上線」後面必須跟著：指令輸出、截圖、或 fresh-context
  agent 的驗收結論。拿不出來就改口「已改動、尚未驗證」。
- 內容正確性靠**與來源論文/報告字面比對**，不靠模型記憶——記憶裡的數字可能過時或
  張冠李戴（見第 1 節「投籃數順序寫反」反例）。
- 驗收不自驗：見 dispatch.md 第 5 節。

## 6. 誠實條款：制度補不了的事

拆解、驗證、多樣本評審能補**執行品質**；以下兩類補不了，遇到就照右欄做，不要硬撐：

| 補不了的 | 遇到時 |
|---|---|
| 品味與美感（視覺、語感、文章骨架是否還是 AI 腔） | 對照 `docs/writing-style-examples.md`，
拿不準就列 2–3 個具體選項讓使用者選，不自行拍板 |
| 模糊需求（使用者自己還沒想清楚要什麼，例如新儀表板的呈現方式） | 先做最小可看的樣品問方向，
不要一次做完整版 |
| 超出可查核來源的知識判斷 | 明說「查不到來源佐證」，標註未證實；絕不編造來源 |
