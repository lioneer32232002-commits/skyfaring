# 制度檔維護協議

> 管的是：`CLAUDE.md`（含其開頭引用的 `AGENTS.md`）與 `docs/agents/*.md`。
> 目標：讓這套檔案保持「短、對、可執行」，不要隨 session 累積成第二份沒人讀的文件。

## 1. 哪些可以自行改（不用問使用者）

- **修過時**：路徑改名、指令失效、工具參數變了 → 發現當場改正，這是義務不是選項
  （優先序條款見下方「資訊衝突時」）
- **補教訓**：踩了新坑 → 按第 3 節格式寫入對應檔案
- **補例子**：judgment.md 的判準缺正例/反例，用本 session 真實案例補上
- **修矛盾**：兩份檔說法衝突 → 以優先序高者為準改掉低者

## 2. 哪些動之前要先問使用者

- **刪除或重寫寫作規範既有規則**（AGENTS.md 明文規定）——只能新增條目或修正明確錯誤
- 改 `.claude/settings.json` 的 hooks，或 `.claude/commands/publish-post.md` 的發文流程
- 改判斷門檻（升降級次數、問人的邊界）
- 大幅重組檔案結構（合併、拆分、搬家）
- 刪掉看不懂用途的規則——看不懂先問，不要當作過時

## 3. 踩坑後教訓寫回哪裡、什麼格式

**寫哪裡**（擇一，別重複寫多處）：
- 通用且高風險、每個 session 都該知道 → CLAUDE.md 對應規範區（一條一行，附一句事故由來）
- 屬於某條判準的新例子 → judgment.md 對應小節的正例/反例
- 派工相關 → dispatch.md 對應小節
- 只是本次工作交接、下個 session 要接手的狀態 → 專案根目錄的 handoff 類文件
  （例如 `TRAFFIC-DASHBOARD-HANDOFF.md` 這類單一主題交接檔，或另立同類檔案）
- 機器狀態、使用者偏好、跨專案事實 → 使用者記憶檔（memory）

**格式**：一行現象 ＋ 為什麼會發生 ＋ 以後怎麼避免（可執行的動作或指令）。
不寫日期流水帳，不貼長輸出。

## 4. 改法（安全程序）

1. 改之前確認 `git status` 乾淨或該檔已 commit——git 歷史就是備份，
   不必另留 `.bak` 副本
2. 用 Edit 精準改，不整檔 Write 重寫（本專案多數檔案是 CRLF，整檔 Write 容易把
   換行符改掉或誤刪別的規則）
3. 改完自查：新舊規則有沒有互相打架？路徑、指令名是否真實存在（用 Glob/Bash 驗，
   例如確認 `scripts/check-post.mjs`、`.claude/agents/data-checker.md` 還在原位）？
4. 制度檔的改動要不要 commit／push，跟一般改動一樣：commit 由主 session 決定是否要做，
   push 到 main 會觸發 Cloudflare Pages 部署（見 dispatch.md 第 7 節），
   不要把還沒驗證過的制度檔改動一起帶上 push

## 5. 長度預算（超了就精簡，精簡屬第 2 節「要先問」）

| 檔案 | 上限 | 超限時 |
|---|---|---|
| CLAUDE.md | 250 行（含引用的 AGENTS.md 內容另計） | 抽細節到 docs/agents/，只留路由與硬規則 |
| docs/agents/ 各檔 | 250 行 | 合併重複、刪已失效段落（先問使用者） |

判斷「該不該加進 CLAUDE.md」的測試：**這條規則是不是每個 session 都用得到？**
不是 → 放進專門檔，CLAUDE.md 最多加一行路由。

## 6. 健康檢查（順手做，不必排程）

任何 session 若發現以下情況，視為制度在退化，當場處理或記入交接文件待辦：
- CLAUDE.md 又出現會過期的數字或歷史敘事
- 同一條規則出現在 3 個以上檔案
- 制度檔引用的路徑/指令已不存在（跑一下就知道）
- `check-post.mjs` 的檢查項與 CLAUDE.md 反面清單走鐘不同步（兩者理論上要一起改，
  見 AGENTS.md「規則維護協議」）

## 資訊衝突時的優先序

`CLAUDE.md`（含 `AGENTS.md`）> `docs/agents/*` > `.claude/commands/*` >
`.claude/agents/*` > README.md > 其他交接文件 > 使用者記憶檔。發現兩處說法不一致：
以高優先序為準，並**當場修正過時的那一方**（怎麼改、哪些要先問，見本檔第 2 節）。
